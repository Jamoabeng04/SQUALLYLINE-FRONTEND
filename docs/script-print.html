Project Manager

How we gathered requirements

"We followed the standard life cycle: problem definition, requirements gathering and analysis, planning and design, implementation, testing, deployment, and now maintenance."

"There are many elicitation techniques; we chose the ones that fit a single expert client. Our primary method was semi-structured stakeholder interviews — open-ended questions about how he runs his studio. Our second was direct observation, or contextual inquiry — we watched him measure a client and run an order end to end. Those were supported by document analysis of his paper measurement books and WhatsApp chats, and by iterative prototyping of mock-ups reviewed with him."

"That gave us our requirements. The functional ones — what the system does — became features like measurement profiles, a catalogue, ordering, and a quote-and-approval workflow. The non-functional ones we grouped as the course teaches: security, performance and scalability, availability and reliability, usability, and compliance."

"We worked Agile and incrementally, prioritising with MoSCoW, shipping a working MVP first and updating the client weekly."

Backend Lead

Architecture, decision records & the live URL

"Squally Line is a classic three-tier client–server web application. The front end is a React single-page app talking to a separate back end over a REST API. The back end is Django with the REST Framework, storing data in PostgreSQL. Both halves deploy independently on Railway — and you can use it live right now at the address on screen."

"Authentication is stateless JWT — short-lived access tokens with rotating refresh tokens. That was a deliberate decision, because it lets us scale the API horizontally later without sticky sessions."

"We logged decisions like that as Architecture Decision Records — ADRs: splitting the SPA from the API, JWT over sessions, and choosing Paystack because it's built for the Ghanaian market and settles in cedis."

"Our third-party systems are Paystack for payments and Railway for hosting, and every library we depend on is permissively licensed — React is MIT, Django is BSD. No copyleft in our tree, so we can legally hand this over as a private commercial product. We verified that with a licence checker."

Demo — the proposal & agreement workflow

Frontend Dev 2 (customer side)"This is the heart of the system — the negotiation between customer and studio, done properly. Backend Dev 1 (server side)"That one click does a lot on the server, all in one atomic transaction. We also built a payment gate: until the deposit is paid, the workshop details stay hidden. The rule 'no work starts without a deposit' is enforced in code, not on trust."

Backend Dev 2

Demo — the staff & admin roles

"The system has three roles, each seeing a different world. A customer sees the shop, their measurements and orders. An apprentice — tailoring staff — runs day-to-day shop-floor operations. An admin — the owner — does everything, including pricing and analytics."

"From the catalogue manager the studio adds products and styles and uploads images — and on upload the back end auto-converts every image to optimised WebP to stay fast. Under Consultations staff review requests, and in the Proposal Editor the studio composes the quote — the other end of the agreement the customer just accepted."

"The Production Queue tracks bespoke work through real stages — pattern-making, cutting, sewing, fitting, finishing, quality check — sorted by deadline and flagging at-risk orders. And the Analytics dashboard gives the owner revenue, top pieces, production stats and customer retention. That's the role-based control the brief asked for."

Backend Dev 1

Security & non-functional requirements

"Because this handles money and personal data, we treated the non-functional requirements as first-class. On security: JWT with rotating, blacklistable refresh tokens; every admin action protected by role-based permissions on the server, not just hidden in the UI; a strong password policy; and every Paystack webhook signature-verified before we trust it. On performance we paginate lists, optimise images to WebP, and refresh tokens silently. On reliability, checkout and proposal-acceptance run in atomic transactions, and the webhook is idempotent, so a repeated callback can't double-charge. Those qualities sit behind the features you just saw."

UI Designer

Limitations & problems we faced

"No honest demo skips its limits. What isn't done yet: the system doesn't send email or SMS — configured but not wired. Refunds are modelled but have no full workflow. Some copy, like care and return policies, is still static. And a couple of interface pieces, like the top profile menu, are on placeholder data — which is why we've used the sidebar throughout."

"The problems we faced were as much practice as code. Coordinating seven people on one codebase meant living in Git branches and real merge conflicts. Learning three.js for the 3D figure took time. Deploying to Railway taught us hard lessons about environment config, CORS and static files. And our biggest management challenge was scope creep — which we controlled with MoSCoW and a scope freeze on the MVP."

Backend Lead then Project Manager

What comes next — is it scalable?

Backend Lead"Is it scalable? Yes — and we can be specific, because the signal to scale is real demand, not ambition. Asked 'what breaks first at ten thousand users?', we'd harden the production config first — secrets and debug into environment variables. Then it's textbook: optimise with indexes and caching, scale vertically on a bigger instance, then scale horizontally — and because our JWT auth is already stateless, many API instances run behind a load balancer with no redesign. First to decompose: media onto object storage and a CDN, plus a background worker for notifications."

Project Manager"On the roadmap after that: real email, SMS and WhatsApp notifications, a full refund flow, and eventually a mobile app. Commercially, since all seven of us are joint authors under Ghana's Copyright Act, we'll assign the IP to the client on final payment, hand over a signed MVP acceptance, and continue on a small hosting-and-support retainer."
